本ファイルは二部構成とする。

1. **実装テスト** — Compose・ランナー・Workflow などハーネス自体の検証（ロジック単位の正常系 / 異常系）

## 共通前提

| 項目 | 値 |
| --- | --- |
| 配置 | リポジトリ直下 `e2e/`（通常の `packages/*/…_test` とは分離） |
| 言語 | **Go（`packages/go`）と JS（`packages/js`）の両方**必須。片方のみでは受け入れない |
| S3 実体 | Docker 上の **RustFS**（MinIO 不使用） |
| Local 実体 | Docker 内の **POSIX ボリューム**上の Local Adapter（ホスト `TempDir` のみは不可） |
| DB | **インメモリ SQLite**（Go: glebarez/sqlite `:memory:` 相当、JS: better-sqlite3 `:memory:`）。方言横断や crudian 内部は信頼し、median が書いたメタの有無・整合のみ見る |
| 入口 | Go: `core.New` → `Store` / `Get` / `Delete` / `PresignGet`。JS: `createMedian` → `store` / `get` / `delete` / `presignGet` |
| 通常 CI | [`ci.yml`](../../.github/workflows/ci.yml) には**含めない** |
| 手動実行 | ローカル任意 + GitHub Actions `workflow_dispatch`（[`e2e.yml`](../../.github/workflows/e2e.yml) 予定） |
| 依存 | Docker Compose、RustFS イメージ（実装時にタグ / digest を pin）、Go toolchain、Node 24+ |

### Update（CRUD の U）の定義

median に独立した **`Update` API は無い**。本 E2E では次を U 相当とする。

1. **内容置換**: `Delete`(id) → 別バイトで `Store` → 旧 id は not-found、新 id のファイルと DB 行が新内容と一致
2. **同一 hash 再 Store**: デフォルトは**既存 id 返却**（DB 行が増えず、メタが不整合にならない）

### 実装固定デフォルト（E2E 環境）

| 項目 | 値 |
| --- | --- |
| RustFS S3 API | Compose サービス名経由（例: `http://rustfs:9000`）、path-style |
| 資格情報 / バケット | テスト専用の固定値（compose / `.env.example`） |
| Presign GET TTL | 出荷デフォルト（1 時間）でよい |
| actor | DB シナリオでは `defaultActor`（または Store オプション）を必ず設定 |
| サムネ | `thumbnails.presets` + `defaultKeys` を 1 key（例: `sm`）に固定 |
| フィクスチャ | CRUD 用: 小さな固定バイト列。サムネ用: 小さな PNG（テスト内生成で可） |

Store 返却: DB あり時は `id` 必須確認。常に `path` / `mime` / `size` / `hash` / `storageKey` を確認。

# 第1部: 実装テスト

ハーネス・起動・ランナーの振る舞い。見出しはロジック（またはコマンド）単位。

## Compose / 起動

### compose up（RustFS + POSIX ボリューム）

- RustFS コンテナと Local 用名前付きボリュームを起動する
- ヘルスチェック通過後に S3 API へ到達できる状態にする
- テスト用バケットが利用可能である（init またはテスト setup で作成）

#### テスト：正常系

- `docker compose up`（または同等）で RustFS が healthy になる
- S3 API ポートへ TCP / HTTP ヘルスが通る
- Local 用ボリュームが runner コンテナから読み書きできるパスとしてマウントされる
- テスト用バケットが存在する（または CreateBucket 後に利用できる）

#### テスト: 異常系

- RustFS が起動しない／ヘルス失敗のとき、E2E ランナーは失敗終了する（偽成功しない）
- 必須環境変数（endpoint・資格情報・バケット・Local ルート）欠落時はランナーが明確に失敗する

### compose down / クリーンアップ

- 実行後にコンテナと一時状態を片付けられる

#### テスト：正常系

- `compose down`（または Workflow の teardown）でサービスが停止する
- 再実行時に前回のオブジェクト残骸に依存しない（バケット空、または一意プレフィックス）

#### テスト: 異常系

- teardown 失敗はログに残る（サイレント無視しない）。ただし本マイルストーンではリトライ網羅は必須にしない

---

## Go E2E ランナー

### e2e/go 実行

- Compose 起動済みの RustFS / POSIX ボリュームに対し、Go のクリティカルシナリオを実行する
- 通常の `go test ./...`（packages/go）とは別エントリ（build tag または `e2e/go` パッケージ）

#### テスト：正常系

- 第2部の必須シナリオ（L1 / S1 / C-L / C-S / T-L / T-S）がすべて成功する
- 終了コード 0

#### テスト: 異常系

- RustFS 未起動・バケット無し・資格情報誤りで S 系が失敗し、非 0 終了する
- Local ルートが未マウント／書き込み不可のとき L 系が失敗し、非 0 終了する

---

## JS E2E ランナー

### e2e/js 実行

- Go と**同一シナリオ**を TypeScript（`@b4moss/median`）で実行する
- 通常の `npm test`（packages/js）とは別エントリ（例: `MEDIAN_E2E=1` または `e2e/js`）

#### テスト：正常系

- 第2部の必須シナリオがすべて成功する
- 終了コード 0

#### テスト: 異常系

- Go ランナーと同様、接続・資格情報・Local ルート不正で非 0 終了する
- Go のみ成功・JS 失敗（またはその逆）の状態は**マイルストーン未達**（両方必須）

---

## GitHub Actions Workflow

### workflow_dispatch（e2e.yml）

- 手動実行専用の Workflow を提供する
- 通常の PR / push では起動しない

#### テスト：正常系

- Actions 上で手動実行すると Compose → Go E2E → JS E2E の順（または同等の直列／明確な依存）で走る
- すべて成功時にジョブ成功となる

#### テスト: 異常系

- `ci.yml` の path filter / jobs に E2E が混入していない
- Go または JS のいずれか失敗で Workflow 全体が失敗する

# 第2部: E2E シナリオ（別枠）

利用者（ライブラリ呼び出し側）のクリティカル経路。  
**実装テストの見出し形式とは分け**、シナリオ ID・前提・手順・期待結果で記述する。

Go / JS は**同じシナリオ ID・同じ手順・同じ期待**を満たすこと。差異は言語 API 名のみ（`Store`/`store` など）。

## 共通（全シナリオ）

| 項目 | 内容 |
| --- | --- |
| 言語 | 各シナリオを Go と JS の両方で実施 |
| ストレージ実体 | Local = Docker POSIX、S3 = RustFS（シミュレーション不可） |
| DB 検証 | インメモリ SQLite。`FindByID`（または同等）で行の有無と主要カラムを確認。crudian 自体の CRUD 網羅はしない |

---

## シナリオ L1 — Local（no-DB）: Store → Get → Delete

**目的:** Docker 内 POSIX 上で、ファイル往復が成立すること（DB 無しの土台）。

**前提:** Local storage、DB 無し。

**手順:** `Store` → `Get`(body) → `Delete` → `Get`（not-found）

**期待:** `size` / `hash` 整合、本文一致、削除後 not-found。

---

## シナリオ S1 — RustFS（no-DB）: Store → Get → PresignGet → Delete

**目的:** RustFS 上でオブジェクト往復と署名付き GET が成立すること。

**前提:** S3 storage、DB 無し、バケット利用可。

**手順:** `Store` → `Get`(body) → `PresignGet` → HTTP GET(URL) → `Delete` → `Get`（not-found）

**期待:** 本文一致、Presign URL の GET 成功・本文一致、削除後 not-found。

---

## シナリオ C-L — Local + DB: CRUD（ファイルとメタ）

**目的:** Local 実体上で Create / Read / Update 相当 / Delete が、**ファイルとインメモリ DB メタの双方**で整合すること。

**前提:**

- Local + インメモリ SQLite、`defaultActor` 設定
- サムネ設定は**付けない**（本シナリオは CRUD に集中）

**手順:**

1. **C（Create）** フィクスチャ A を `Store`。返却 `id` / `path` / `hash` / `size` を記録
2. DB で `id` の行を読む（`path` / `mime` / `size` / `hash` / `created_by` / `owned_by`）
3. **R（Read）** `Get`（id、body 付き）で本文・メタ一致
4. **U-a（同一 hash 再 Store）** 同じバイトを再度 `Store` → **同じ `id`** が返る。DB の当該行が壊れない（hash/path 維持）
5. **U-b（内容置換）** `Delete`(id A) のあと、異なるフィクスチャ B を `Store` → **新しい `id`**。旧 id は DB not-found、新 id のファイルと DB が B と一致
6. **D（Delete）** 新 id を `Delete` → ファイル Get not-found、DB 行 not-found

**期待結果（要約）:**

| 段階 | ファイル | DB |
| --- | --- | --- |
| C | オブジェクト存在 | 行が存在し主要カラム一致。`created_by` = `owned_by` = actor |
| R | 本文一致 | （Get 経由でメタ一致） |
| U-a | 実体は既存のまま | 同一 id、行が増えない |
| U-b | 旧消滅・新存在 | 旧消滅・新行が B と一致 |
| D | not-found | not-found |

---

## シナリオ C-S — RustFS + DB: CRUD（ファイルとメタ）

**目的:** C-L と同じ CRUD を RustFS 上で行う。加えて Create 後に `PresignGet` → HTTP GET で本文一致を 1 回確認する。

**前提:** S3 + インメモリ SQLite、`defaultActor`。サムネ無し。

**手順:** C-L と同型。Create 直後（または Read 時）に Presign 検証を挟む。

**期待:** C-L と同じファイル/DB 整合 + Presign GET 成功。

---

## シナリオ T-L — Local + DB: サムネイル生成

**目的:** 画像 Store 時のサムネ生成が、**Local 実体・返却 variants・DB 子行**で正しいこと。

**前提:**

- Local + インメモリ SQLite、`defaultActor`
- `thumbnails.presets` に 1 key（例: `sm`）、`defaultKeys: ["sm"]`
- 入力は小さな PNG

**手順:**

1. PNG を `Store`
2. 返却に親 `id` と `variants`（key=`sm`）があること。`variants[].path` / `size` / `hash` / `width` / `height` を記録
3. 親 path と variant path の両方を `Get`(body) でき、バイト長が `size` と整合
4. DB: 親行は `original_id` / `variant_key` が空（NULL）。子行は `original_id` = 親 id、`variant_key` = `sm`、path/hash が返却と一致
5. 親 id で `Delete`
6. 親・子ともファイル Get not-found、DB も親・子 not-found（カスケード）

**期待:** サムネ実体が Local に存在し、DB 親子が契約どおり。親削除で子ファイル・子行も消える。

---

## シナリオ T-S — RustFS + DB: サムネイル生成

**目的:** T-L と同じサムネ契約を RustFS 上で満たすこと。

**前提:** S3 + インメモリ SQLite、サムネ 1 key、小さな PNG。

**手順:** T-L と同型（実体は RustFS オブジェクト）。

**期待:** T-L と同じ（variants 実体・DB 親子・カスケード削除）。

---

## シナリオ行列（受け入れの見方）

| シナリオ | 軸 | DB | 内容 | Go | JS | 必須 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 | Local | なし | ファイル往復 | 通ること | 通ること | はい |
| S1 | RustFS | なし | ファイル往復 + Presign | 通ること | 通ること | はい |
| C-L | Local | インメモリ | CRUD + メタ整合 | 通ること | 通ること | はい |
| C-S | RustFS | インメモリ | CRUD + メタ + Presign | 通ること | 通ること | はい |
| T-L | Local | インメモリ | サムネ + DB 親子 + カスケード | 通ること | 通ること | はい |
| T-S | RustFS | インメモリ | 同上 on S3 | 通ること | 通ること | はい |

全セル成功で本マイルストーンのシナリオ受け入れとする。
